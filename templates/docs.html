How Track Pulse works

Arrival times today are built from the timetable plus the current delay. That ignores what every controller knows: some stretches have slack and trains win time back there, others lose time almost every day. Track Pulse learns both from real running and predicts the arrival at every station ahead.

What it does

Given a train, the station it is at and how late it is, Track Pulse predicts how late it will be at each later station, with a likely range. Live positions arrive every five minutes; each one updates the arrival times on the website, in the API and on the station boards.

Example from the home page: Kaveri Express leaves Katpadi 30 minutes late. Carrying the delay forward says KSR Bengaluru 30 minutes late. Past runs show the last few kilometres into Bengaluru are timetabled at 36 minutes for 4.3 km, so a late train almost always wins most of that back.

The data

Every stop of every run of the trains we follow: scheduled and actual times, distance and position at each station. {{ trains }} trains on {{ corridors | length }} corridors are followed from the start, from three-hour Shatabdis to the Kerala Express, which runs for about 50 hours across 3,000 km. Any of {{ "{:,}".format(all_count) }} trains across India can be opened: the first time someone does, the site fetches its last 90 days of runs, and from then on the feed follows it too.

The Chennai and Bengaluru trains have history since November 2021 from a public Kaggle dataset. The others were collected from the same live source the feed uses, back to March 2025. The live feed adds each day’s runs for every train.

Weather: daily rain and coldest temperature from Open-Meteo, for each 50 km square a route passes through, recorded for past days and forecast for the next three.

Live positions come from two sources, merged on every pass: the public whereismytrain.in cache and RailRadar. For each station the feed keeps whichever saw the train later; the cache can lag by an hour, and either one going down does not blank the site. Station names come from the open datameet railways list.

Cleaning keeps only stations that actually reported, drops the handful of diverted or misreported runs (more than 2 hours early or 10 hours late), and computes delay from the timestamps, so trains running early show as negative instead of being floored at zero.

Why machine learning beats similar past runs

Similar past runs answer one question well: what happens to a train this late at this station. They can’t see the hour, the season, or that this week a speed restriction is slowing everyone between two stations. The learned models get the similar-runs answer as a starting point and learn corrections from those extra inputs. The largest single gain came from the recent-runs input: adding it cut test error by roughly one to two minutes for every learned model.

{% if models.best == "blend_lightgbm+hist_gboost" %}

Why boosted trees on absolute error

Both halves of the model in use are boosted trees fitted on absolute error. Boosting suits this problem because delay recovery is made of interactions (a late train, on a stretch with slack, at night) that trees capture and straight lines can’t. Absolute error suits it because delays have a long tail: a few runs are hours late, and a model fitted on squared error bends towards them. Fitting on absolute error aims at the typical run, which is what a passenger experiences, and it is the same measure we score with.

Why this combination

The blend averages LightGBM and histogram gradient boosting. They share those assumptions but build their trees differently: LightGBM samples rows and inputs at random for each tree, while histogram gradient boosting uses every row and handles the train number as a category. So their mistakes differ a little, and averaging cancels part of them. When this blend was chosen it beat each of its halves on validation, and on a tie with a three-model blend the simpler one was kept.

The model

Track Pulse runs our own machine-learning model, trained on years of real running. We tried several kinds of model against two baselines, delay carried forward and similar past runs, and keep the one that is most accurate on months it never saw. Every night it is retrained, and a new version replaces the one in use only if it is more accurate.

How we test

  1. Split by date, never at random. The model learns from older runs and is tested on newer ones, as it would be used. A random split would let it learn from the same week it is tested on.
  2. No peeking at the answer. The similar-runs input for any example is computed only from runs before that example’s time window.
  3. Three windows. Learn, then validate to choose the model, then test once to report. The test months play no part in any choice.
  4. Same questions as real use. Every reporting station of every test run is treated as “now”, and every later station is predicted: {% if acc %}{{ "{:,}".format(acc.all.predictions) }} predictions over {{ acc._meta.tested_on }}{% endif %}.

Which method answers when

Every arrival time comes from one of three methods. The website and the API show which one, in the method field.

  1. Load the latest history and model. Every {{ refresh_min }} minutes the server reloads, so newly saved runs and a newly retrained model take effect without a restart.
  2. Find similar past runs for each station ahead: the {{ k }} runs that were about as late here and how their delay changed by that station. This always runs, because it is one of the model's inputs.
  3. ML model (model), when a trained model exists and the train is at a timetabled halt. This is the normal case. If there are no runs from the last {{ recent_days }} days, the model still answers: {{ (drop_recent * 100) | round | int }}% of its training examples had the recent-runs input deliberately blanked, so it learnt to do without.
  4. Similar past runs (similar_runs), when there is no trained model, or the train is at a station that is not a timetabled halt. The median of the similar runs is used directly.
  5. Current delay carried (carried), only when there is no trained model and fewer than {{ min_runs }} comparable runs. The prediction is marked “thin history”.

New, special and diverted trains get learnt arrival times from their first run. Until a train has {{ min_runs }} runs, its stations come from its latest timetable and the model answers from how all trains behave on comparable stretches (its own-history inputs are simply blank, as the model was trained to handle). The train page says how many runs it has so far.

The range (P10 to P90) comes from the model's measured errors, not from the similar runs; see below.

P10, P50 and P90

Every arrival time comes as three numbers:

  • Expected (P50): our best estimate. Half of trains in this situation arrive before it, half after.
  • Earliest likely (P10): only 1 in 10 arrive earlier.
  • Latest likely (P90): only 1 in 10 arrive later.

So 8 in 10 trains arrive between P10 and P90. The window is not a guess: it is set from how far off the model really was on 90 days of runs it never saw, separately for each train and for how far ahead the station is (next hour, 1 to 3 hours, 3 to 8, 8 to 24, more than a day). It is narrow for the next station and wide a day ahead, because that is how uncertainty really grows. Trains without enough test runs use the all-trains window. {% if self_check.scored and self_check.inside_range is not none %}In live use over the last {{ self_check.days }} days, {{ (self_check.inside_range * 100) | round | int }}% of trains arrived inside it (target 80%).{% endif %}

Spotting recovery

A recovery is a train winning back 5 or more minutes between two stations. For every train, the test counts how many recoveries happened on runs the model never saw, how many the model predicted, and how many predicted recoveries really happened. It also lists the stretches where each train recovers most, with real against predicted minutes. {% if acc and acc.recovery %}{% set rs = acc.recovery.values() | list %}{% set n = rs | sum(attribute='recoveries') %} Across all trains: {{ "{:,}".format(n) }} recoveries tested.{% endif %}

Carrying the delay forward, which is how most running-status displays estimate, predicts none of them: it assumes a late train never catches up. Each train page shows its own numbers under "Where it wins back time".

One train's delay to another

Delay spreads along a line. Track Pulse uses it in two ways:

  • As a model input: how many other trains reported on the next 200 km in the last 2 hours, how late they were and whether they were losing time. A slow line ahead shows up here before this train reaches it.
  • On the train page: trains in front going the same way (they can hold this one up), trains coming the other way (they share stations and platforms), and trains behind going the same way. For those behind, if this train is expected more than 15 minutes late at a station they share, they are marked at risk of being held up.

Direction comes from comparing the two trains' whole routes, not just one shared station.

Unscheduled halts

If a live train has not reported at its next station although even a slow run (its P90) would have got there more than 15 minutes ago, it is flagged "Possibly held": at a signal, for a crossing, or by a fault. Its arrival times then assume it moves again now. A missed report in the source can also trigger it, so it is a prompt to look, not a certainty.

Against other estimates

Each time the feed records a train's position, it also saves RailRadar's own forecast made from the same moment. When the train arrives, both are scored against the real time, along with carrying the delay forward, on exactly the same arrivals.{% if rivals.scored %} Last {{ rivals.days }} days: Track Pulse {{ rivals.ours }} min average error, RailRadar {{ rivals.railradar }} min, delay carried forward {{ rivals.carried }} min, on {{ rivals.scored }} arrivals.{% endif %} Whereismytrain's public data only repeats the timetable for stations ahead, so there is no forecast of theirs to score.

Station boards, map, control room

  • Stations: a display board for any station, every train on its way with expected time and P10 to P90, refreshed every minute. The same data is in /api/stations/<code>/arrivals for real screens.
  • Map: every operational line in India, single and double track, with the live trains coloured by status. Single lines are where trains wait to cross, so delay spreads fastest there.
  • Control: every running train on one screen, worst first, with held trains, late trains with others following on the same line, and platform clashes: two trains expected at one platform within 5 minutes, from the platform and times RailRadar expects.

Why it's late

Every ML prediction lists the two things that pushed it most, in minutes. These are SHAP values: starting from the average delay change the model has learned, each input gets the share of the difference it caused, and the shares add up exactly to the model's answer. We group the {{ features | length }} inputs into plain reasons: how late the train is now, similar past runs, the last {{ recent_days }} days on this stretch, distance to go, time of day, day and season, and the train and section itself.

Example: "last {{ recent_days }} days on this stretch +6" means trains have been losing time here lately (a speed restriction or works, say), and that alone adds about 6 minutes to this prediction.

Reasons are shown for ML predictions only; the similar-runs and carried methods explain themselves.

Train status

Every running train gets one label, so a control room can see at a glance which trains need attention. It is based on the worse of two numbers: how late the train is now, and how late it is predicted to be at the last station we can predict. A train that is on time now but heading into a stretch where it usually loses time is flagged before it loses it.

  • Normal: under {{ delayed_min }} min late, now and ahead.
  • Delayed: {{ delayed_min }} to {{ disrupted_min - 1 }} min late.
  • Disrupted: {{ disrupted_min }} min or more. Passengers will likely miss connections; worth a look.

The "Running now" table lists disrupted trains first. The same label is in the control API as status.

Checking itself

Every arrival time handed out for a live position is logged. When the train actually reaches that station, the feed saves the real time and the two are compared. The home page and /api/accuracy/live show the result.

Every night at 03:00 the feed fetches the latest weather, retrains every model on the newest runs (including trains opened that day), and re-runs the test on unseen runs, which also recalibrates P10 and P90 and the recovery numbers. The new winner replaces the model in use only if it is at least as accurate on the newest test months, so one bad day of data can’t make arrival times worse.

Live data and when it pauses

Every 5 minutes the feed asks two public sources about every train it follows: the whereismytrain.in cache and RailRadar. For each station it keeps whichever saw the train later, so one source lagging or failing does not hold the site back. It records the position, saves every observed stop for learning, logs RailRadar's forecast for the head-to-head, and saves expected platforms for the clash check.

After each full pass the feed writes a heartbeat. If none arrives for 15 minutes, every page says live updates are paused and that it is showing each train's last known position, with arrival times worked out from it. Trains that have not reported for 3 hours leave the live views.

Limits

  • A station can only be predicted if it has reported in past runs. Some terminal stations never report in the source data, so a few routes end one or two stations early.
  • Live positions come from public third-party sources. In service, they would be replaced by NTES or RTIS through the same API, with no change to the model.
  • New trains are predicted by a model trained on the trains followed so far until the nightly retrain includes them; the cascade view and congestion inputs only see trains the site follows.
  • Congestion is measured only from the trains we follow. With every train on the network in the feed, the same inputs would see the full traffic on a line.
  • GPS positions and signal aspects are not public. The model uses station reports instead; with RTIS GPS it would get a position every few seconds through the same API.
